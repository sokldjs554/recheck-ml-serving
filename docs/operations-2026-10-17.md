해당 창의 메모리 표본은 약 146~305MB, 한도는 약 537MB였다. 로그에서 OOM 근거는 확인하지 못했다. 개별 모듈 import·플랫폼 스케줄링·DB 초기 연결의 소요 시간을 분리 측정한 것은 아니므로, 이들이 지연에 기여한 비율은 미확정이다.

## 수정과 비용

- `scripts/serve_demo.py`: 모델 초기화에 **monotonic clock 기준 최대 90초**를 허용한다. 개별 health 확인과 대기도 남은 시간 안으로 제한한다. 모델이 실제로 종료되면 즉시 실패하며, 준비되지 않은 모델에 API를 연결하지 않는다.
- 시작·모델 준비·시간 초과·자식 종료를 이벤트 이름과 경과 시간으로 기록한다. 요청 본문·인증 정보는 기록하지 않는다.
- `backend/recheck/model.py`: 학습용 sklearn import를 학습 함수로 이동하고, ExtraTrees는 CPU ensemble 학습에서만 가져온다. 공개 lightweight 번들을 읽을 때 불필요한 tree ensemble 모듈을 로딩하지 않는다. 모델·해시·예측 계약과 CPU workload는 유지한다.
- 비용: 영구적으로 준비되지 않는 모델은 기존의 빠른 연결 거절 경로보다 최대 약 60초 더 기다린다. 그 대신 정상적으로 느린 초기화를 실패로 오인해 반복 재시작하는 문제를 줄인다. 이는 **시작 제한 변경**이며 공개 점검의 **5초 기준·90초 HTTP timeout·분모·실패 판정**은 변경하지 않았다.

## 검증과 해석

전체 백엔드 **151개 통과**(SQLite, 실제 loopback HTTP 포함). 새 6개는 시작 경계 5개와 번들 import 검사 1개다. 첫 제한된 샌드박스 실행은 기존 프로세스 풀 검사가 IPC 제약으로 멈춰 종료했으며, 로컬 IPC를 허용한 실행에서 전체를 다시 검증했다.

수정 전에는 가상 시계로 35초 뒤 준비되는 모델을 재현했을 때 30초에 종료됐다. 수정 후 같은 재현에서 API가 시작되고 정상 종료한다. 끝내 준비되지 않는 경우, 모델 프로세스 종료, 느린 health 확인의 공통 deadline, 초기화 중 SIGTERM도 검사한다. 가상 시계 검사는 실제 35초 성능 측정이 아니다.

실제 로컬 두 프로세스·준비된 lightweight 번들·SQLite에서는 health 준비까지 2.775초, 이후 여섯 HTTP 단계의 점검은 55.735 / 32.592 / 25.321ms였다. SIGTERM 후 자식들을 정리하고 종료 코드 0을 확인했다. **Render cold start 또는 PostgreSQL 성능으로 해석하지 않는다.**

## 남은 운영 제약

[Render 무료 서비스 문서](https://render.com/docs/free#spinning-down-on-idle)는 15분간 요청이 없으면 중지하고 다음 요청에 다시 시작하며, 이 과정에 약 1분이 걸릴 수 있다고 설명한다. 이번 로그는 요청 중 프로세스 시작과 재시작을 확인해 주지만, 플랫폼의 idle 전환 이벤트와 모든 대기 구간을 직접 수집한 것은 아니다.

따라서 이 수정은 확인된 **조기 종료 결함**을 해결하는 것이며, 무료 공개 환경의 최초 요청이 5초 이내가 된다는 보장은 아니다. 서버를 먼저 깨운 표본만 집계하거나 점검 빈도를 높여 idle을 숨기지 않는다. 이후 공개 검증도 시작 시각·배포 커밋·전체 표본과 함께 해석해야 한다.

[10/13의 54.037초 실패](https://github.com/sokldjs554/recheck-ml-serving/actions/runs/38328704268)는 그대로 유효하다. 당시 단계별 시간이 없었으므로 이번에 확인한 조기 종료가 당시 원인이었다고 소급해서 단정하지 않는다.

설정 대조에서 `render.yaml`의 `healthCheckPath: /health`와 달리 실제 서비스의 HTTP health-check 경로는 비어 있었다. 외부 점검은 `/health`의 DB·모델 검증을 실행하지만 Render 배포 준비 판정에도 이를 사용하도록 일치시킬 필요가 있다. 현재 연결된 Render 도구에는 기존 서비스의 이 필드를 변경하는 기능이 없어 미반영이다. Dashboard의 해당 서비스 Settings → Health Check Path를 `/health`로 지정하는 관리 설정 작업이 남는다. 새 서비스 생성이나 유료 전환으로 대체하지 않았다.
