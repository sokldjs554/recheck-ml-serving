# 90초 시연 대본

**0–20초 — 문제 선택**

“AI가 응답한 직후 입력 정보가 바뀌면, 그 답을 계속 믿어도 될까요? 저는 점수를 한 번 반환하는 기능보다 그 판단을 사용할 수 있는 조건에 관심을 가졌습니다.” 모드를 먼저 보여준다. 브라우저 시뮬레이션이면 그렇게 밝히고, 서버 시연이면 Python 서버 연결 표시를 확인한다.

**20–45초 — 실패 재현**

‘정보 변경 재검증’을 끄고 ‘오래된 판단 재현’을 누른다. 오래된 결과가 통과하는 상황을 보여준다. 재검증을 켜고 같은 버튼을 다시 눌러 결과가 무효가 되는 이유를 버전과 처리 시간으로 설명한다. ‘지금 사용 가능한지 확인’으로 사용 직전 검증도 보여준다.

**45–65초 — 운영 실패**

모델 응답 지연이나 중단을 주입한다. 무한 로딩이나 근거 없는 정상 응답 대신 확인 필요 상태를 반환한다. 사용자가 보는 안내, 서버의 사유 코드, 추적 정보를 연결해 설명한다.

**65–90초 — 본인의 판단과 기여 방향**

“저는 AI와 개발할 때 반복 오류를 직접 조사하고 대안을 비교했습니다. 이번에는 그런 과정을 재현 가능한 테스트로 남겼습니다. 토스뱅크에서는 상품팀이 AI를 도입할 때 최신성 검증, 실패 시 응답, 관측 방법을 공통 기반으로 제공하는 데 기여하고 싶습니다.”

## 예상 질문

- 왜 추론 전에만 확인하지 않았나? 추론 중 입력이 바뀌는 경쟁 조건이 있기 때문이다.
- 결과 저장 후 바뀌면? 다음 단계에서 검증한다. 이 데모는 실제 원장 커밋을 구현하지 않는다.
- 모델을 왜 작게 골랐나? 합성 데이터의 실제 추론과 서버 동작을 재현하기 위해서다. 사기 탐지 정확도 경쟁은 범위가 아니다.
- 왜 모든 요청을 처리하지 않나? 수용량을 초과한 대기는 지연·메모리 문제를 키운다. 거절과 유효 응답을 나눠 측정한다.
- 왜 Kafka가 없나? 필요가 확인되지 않은 운영 복잡도를 먼저 추가하지 않았다.
- 실제 운영 성과인가? 개인 프로젝트 실험 결과다. 은행 고객 수나 손실 예방 성과로 확대하지 않는다.

## 면접 전에 본인이 직접 해볼 일

테스트 한 개를 골라 보호 로직을 제거했을 때 실패하는지 확인한다. 추론 시간 예산을 바꾸고 지연과 유효 응답 수의 변화를 설명한다. 버전 검증의 한계와 모델 데이터의 한계를 자신의 말로 설명한다. 기존 AI 협업 경험의 실제 오류·원인·자신이 제안한 대안은 본인의 기록으로 보완한다.
