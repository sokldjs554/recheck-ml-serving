# 정합성 테스트와 시간 예산 테스트 분리

2026-10-11 CI [첫 실행](https://github.com/sokldjs554/recheck-ml-serving/actions/runs/38146420626/attempts/1)에서 두 검사가 실패했다. 같은 코드의 재실행 통과는 원인 해결로 세지 않는다.

- `test_fence_and_update_race_over_independent_connections`: PostgreSQL `FOR UPDATE`가 운영 설정의 100ms 잠금 대기를 넘겨 `LockNotAvailable`을 냈다. 테스트는 모든 트랜잭션 성공을 전제했지만 운영 계약에는 잠금 대기 실패가 허용된다.
- 기존 HTTP 통합 검사: 첫 요청의 `clear` 기대에 `review`가 반환됐다. 당시 assertion이 응답 원인을 기록하지 않아 해당 실행의 정확한 reason은 복원할 수 없다. 검사 구조가 첫 요청, 추적, 50ms 변경 창, 100ms 시간 제한을 한 테스트에 묶고 있었다.

## 수정한 검증 경계

DB 정합성 테스트의 연결에만 잠금 대기 5초·statement 10초를 설정한다. 운영 코드의 PostgreSQL 100ms / SQLite 100ms 잠금 예산은 바꾸지 않는다. 별도 테스트는 **운영 기본 설정**에서 실제 다른 연결의 잠금을 유지해 실패를 발생시키고, 미검증 결과가 저장되지 않았는지 확인한다. 잠금을 풀고 같은 요청을 재개하면 변경된 버전 때문에 무효화되며, 같은 키 재요청은 같은 결과를 반환해야 한다.

HTTP 정합성 검사는 준비 상태를 확인하고 2초의 테스트 예산 안에서 추적과 변경 무효화를 검증한다. 실제 worker의 active 상태를 관측한 뒤 변경한다. **100ms 시간 제한은 별도 HTTP 프로세스 검사**에서 그대로 검증하며, 전파된 제한을 넘기는 요청은 정상 판단을 반환하지 않아야 한다. 원인과 전체 응답을 assertion에 남긴다. 프로세스가 준비됐다는 사실을 첫 추론 100ms 성능으로 대신하지 않는다.

CI는 이 두 파일을 PostgreSQL·실제 HTTP 프로세스로 세 번 반복한다. 재실행으로 실패를 지우지 않고, 어느 회차든 실패하면 전체 검증을 실패시킨다. 이는 반복 안정성의 제한된 확인이며 성능·장기 가용성 측정이 아니다. 부하 성능의 근거는 [별도 실험](compute-experiments.md)에 있다.
