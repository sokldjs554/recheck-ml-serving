# RECHECK: evidence to action case study

User intent: strengthen a junior Python/AI portfolio after a candid 6.5–7/10 review. The user authorized implementation and publication, and previously rejected repeated approval gates. A numerical rating, human feedback, personal authorship, production impact, or employment outcome must not be fabricated.

The central demonstration is a support draft based on a document that changes before use. Keep the existing advanced labs but make a concise guided real-API case the default entry. No giant hero. Use compact headings, an adjacent source/draft comparison, a visible event sequence and one next action. On connection failure show an explicit failure with retry; never silently simulate results. Preserve all existing routes and checks.

Close the point-in-time gap only for an owned synthetic action: recording a support task in the same database transaction as evidence validation. This is not sending a message, transferring funds, or atomically coordinating an external system. Add bounded immutable action records, idempotent retries, request-body conflict rejection, session isolation and same-lock serialization with document changes. A replay returns the original historical action, not a fresh validity assertion. Public APIs do not expose unsafe execution modes.

A separate reproducible adversarial experiment compares trust-at-creation, check-then-act, and atomic guarded recording on the same ordered events. Use real SQL state and the production guard; unsafe baselines live only in scripts. Include current, cited edit, unrelated edit, delete, expiration, release switch, revision ABA, and duplicate action cases. Report denominators, stale acceptance, false rejection, duplicates and exact scope; no toy retrieval quality or throughput inflation.

The UI defaults to a first-visit guided case, with source edit and blocked old draft, then paired rebuild and fresh task recording. Advanced links expose the existing free-form experiments. Another compact section presents actual measured comparison (with source link and explicit fixed-schedule scope), and developer exercises with evidence requirements. Human usability testing remains unperformed until actual participants provide results.

Review focus: delayed completion after reset/unmount; API error must clear success; idempotency after source changes; concurrent edit/action must have a valid serialization; persisted browser notes must not be represented as verified candidate contribution.
