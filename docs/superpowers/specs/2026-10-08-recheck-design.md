# RECHECK Design

토스뱅크 ML Backend Engineer 지원 프로젝트로 **RECHECK**를 제안한다. AI 확인 결과를 생성한 뒤에도 입력 데이터와 정책이 바뀌면 그 결과의 사용 가능 여부를 다시 검증하는 서버다. 면접관은 송금 전 확인을 모사한 화면에서 장애와 데이터 변경을 직접 발생시키고, 고객 안내·분산 추적·판단 기록이 어떻게 연결되는지 확인한다.

이 문서는 2026년 10월 8일 확인한 공개 자료를 바탕으로 한 조사 및 설계 초안이다. 구현·배포·성능 검증은 아직 진행하지 않았다. 지원자는 신입이며 Python·LLM·AI/ML 경험이 있다. AI와 함께 개발하면서 반복되는 오류를 직접 조사하고, 서로 다른 해결 방법을 비교·통합해 해결한 경험을 제공했다. 아래 소개 문구는 이 경험을 바탕으로 한 제안이며 미확인 세부 이력이나 성과를 추가하지 않는다.

## 공고가 요구하는 증거

[공식 공고](https://toss.im/career/job-detail?job_id=6600650003)는 ML Service Team의 서버·공통 플랫폼 개발, 무거운 AI 연산의 안정적인 응답 속도와 처리량, MSA 분산 추적을 강조한다. Python·Kotlin·Go 중 하나 이상의 서버 개발 및 운영 경험이 필요하고, Kubernetes와 높은 SLA 서비스 운영 경험은 우대 사항이다. ML 경험 자체는 필수가 아니다. 이력서에서는 구현 사례, 기술적 고민, 복잡도와 개발 비용의 비교, 실제 운영 및 성과 개선을 설명하도록 권한다.

| 공고의 요구 | 프로젝트에서 제시할 증거 |
| --- | --- |
| 안정적인 AI 서빙 | 제한된 동시 실행 수, 대기열 상한, 요청 시간 예산, 타임아웃 후 확인 필요 응답 |
| 분산 추적 | API와 모델 서버를 잇는 실제 OpenTelemetry trace |
| 견고한 서버 설계 | 데이터 갱신과 추론 완료가 경쟁하는 상황의 재현 테스트 |
| 운영 및 모니터링 | 요청 수·유효 응답·거절·타임아웃을 구분하는 지표와 장애 대응 기록 |
| 비용과 복잡도 판단 | 단일 프로세스 기준선과 모델 서버 분리의 측정 비교 및 ADR |
| Kubernetes | 배포 설정, readiness, 종료 시 진행 중 요청 처리, 실제 기동 여부를 구분한 검증 기록 |

이 프로젝트의 실험 기록은 실제 은행 프로덕션 운영 경력을 대체하지 않는다.

## 차별화할 지점

공개 사례에서 가져올 것은 특정 주제나 기술 목록보다 **문제를 발견하고, 선택의 근거를 남기며, 결과를 검증하는 방식**이다. RECHECK는 여기에 면접관이 직접 실행할 수 있는 실패 재현을 더한다.

가장 중요한 질문은 “모델이 답했는가”에서 한 단계 더 나아간 **“그 답이 현재 데이터와 정책에서도 사용할 수 있는가”**다. 정상 상태의 점수 화면, 정보가 바뀐 직후의 오래된 결과, 모델 장애 중의 확인 필요 응답을 같은 화면에서 비교한다. 이는 이 조사 범위에서 선택한 차별화 방향이며, 세계 최초의 기술이라는 주장은 아니다.

| 후보 | 장점 | 이번 프로젝트에서의 판단 |
| --- | --- | --- |
| RECHECK 판단 유효성 검증 | 서버 정합성·장애 대응·고객 안내를 하나의 상황으로 설명 | 추천 |
| 문서 누락을 찾는 AI 심사 보조 | 고객 불편과 결과물이 눈에 보임 | 추출 정확도와 데이터 확보가 주제를 지배할 수 있음 |
| 범용 추론 게이트웨이 | 배칭·트래픽 제어·비용 계측에 집중 가능 | 은행에 기여할 구체적 장면이 약해짐 |

## 지원자로서 전달할 메시지

제안하는 중심 문장은 다음과 같다.

> 저는 Python과 AI/ML을 경험한 신입 개발자로, AI와 개발하면서 반복되는 오류를 직접 조사하고 서로 다른 해결 방법을 비교해 해결해 왔습니다. RECHECK에서는 이 태도를 서버 설계로 확장해, 실패를 재현하고 원인 가설을 검증하며 같은 오류의 재발을 막는 과정을 보여주려 합니다.

토스뱅크에 기여하고 싶은 방향은 상품 조직이 AI 기능을 도입할 때 요청 시간 예산, 데이터 최신성, 장애 시 대체 응답, 관측 방법을 매번 새로 만들지 않도록 공통 서버 구성 요소로 제공하는 것이다. 실제 토스뱅크 내부에 이 기능이 없다고 가정하지 않으며, 입사 후 현행 구조와 필요를 먼저 확인해야 한다.

최종 지원 문구에는 직접 이해하고 설명할 수 있는 구현·실험만 담는다. AI 도움을 받은 범위, 본인이 검토·수정한 판단, 남은 한계도 개발 기록에 남긴다. 금융 손실 예방액이나 고객 이탈 감소율은 운영 데이터가 생기기 전까지 주장하지 않는다.

## 제품 범위와 상태

가상의 송금 전 위험 신호 확인을 사용한다. 실제 계좌 조회·송금·거래 승인은 수행하지 않는다. 모델 입력은 합성 거래 특징이며 데모에서 이를 명확히 표시한다. 고객 화면은 “현재 확인된 주의 신호 없음”, “추가 확인 필요”, “정보가 변경되어 다시 확인 중”을 구분한다. 주의 신호 없음은 금융 안전 보증이 아니다.

판단 기록에는 요청 식별자, 입력 특징의 버전, 모델 아티팩트 해시, 정책 버전, 생성 시각, 만료 시각, 결과와 사유, trace ID가 포함된다. 기록의 해시는 재현 대상의 식별용이며 별도 서명 체계 없는 위변조 방지를 주장하지 않는다.

결과의 상태는 생성 완료, 정보 변경으로 무효, 유효기간 만료, 재확인 필요로 구분한다. 당시 판단 기록은 수정하지 않고, 현재 사용 가능 상태를 별도로 계산한다. 동일한 멱등 키로 다른 요청을 보내면 충돌로 거절하며, 같은 요청의 중복 호출은 새로운 판단을 중복 생성하지 않는다.

## 서버 구조와 데이터 일관성

Python FastAPI API 서버, 별도 모델 서버, PostgreSQL, React와 TypeScript 데모 화면을 기본 구성으로 한다. HTTP 경계를 기준으로 API와 모델 연산을 분리해 자원 경합과 장애를 관찰한다. 초기 버전은 Redis와 Kafka를 도입하지 않고, 필요한 구성 요소를 추가할 때마다 측정 근거를 남긴다.

1. API가 입력 특징과 버전, 활성 모델·정책 버전을 읽는다.

2. 남은 시간 예산과 모델 서버의 수용 가능 여부를 확인하고 추론을 요청한다.

3. 추론 뒤 짧은 DB 트랜잭션에서 버전을 다시 비교한다. 추론을 기다리는 동안에는 DB 잠금을 잡지 않는다.

4. 버전이 같으면 판단 기록을 저장한다. 달라졌거나 만료됐으면 이전 결과를 사용 가능한 결과로 발급하지 않는다.

5. 고객이 다음 단계로 이동하는 모사 동작에서도 판단의 버전과 만료를 다시 확인한다. 화면 갱신이 늦어도 서버 검증을 우회할 수 없도록 한다.

특징 갱신과 최종 검증은 같은 버전 행을 짧게 잠그고 일관된 잠금 순서를 사용한다. PostgreSQL의 [행 잠금](https://www.postgresql.org/docs/current/explicit-locking.html)을 토대로 검증 시점의 경쟁을 제어한다. 검증 직후 미래의 데이터 변경까지 막는다는 보장은 하지 않는다. 실제 송금 승인과 원장 커밋의 원자성은 이 데모 범위 밖이다.

API와 모델 서버는 [OpenTelemetry context propagation](https://opentelemetry.io/docs/concepts/context-propagation/)으로 trace를 연결한다. 로그에는 합성 요청 식별자와 버전·사유를 기록하고 원본 민감정보를 담지 않는다.

## 모델 서빙과 실패 처리

고정 시드의 합성 데이터로 작은 분류 모델을 학습하고 별도 서버에서 실제 추론한다. 데이터 생성기·학습 코드·평가 분할·아티팩트 해시를 함께 제공한다. 합성 데이터 평가 결과는 실제 사기 탐지 성능으로 해석하지 않는다.

무거운 연산과 지연의 실험은 실제 CPU 연산을 수행하는 모드와 명시적인 지연 주입 모드를 분리한다. 지연 주입 결과를 실제 모델의 성능으로 보고하지 않는다. 배칭은 단건 처리와 비교 측정 후 이점이 있을 때 채택한다.

요청 시간 예산은 데모 기본값 300ms로 시작하되 실험용 정책 값임을 표시한다. 동시 실행·대기 요청 상한을 둔다. 타임아웃, 과부하, 특징 조회 실패, 모델 버전 불일치는 모두 사유가 다른 확인 필요 응답으로 분류한다. API 타임아웃만으로 모델 연산이 중단된다고 가정하지 않고 모델 서버의 작업 수를 끝까지 계측한다. 무제한 재시도는 하지 않는다.

모델 버전 교체는 새 아티팩트 준비와 readiness 확인 뒤 적용한다. worker의 실제 모델 해시와 요청 모델 버전이 다르면 응답을 사용하지 않는다. Kubernetes 배포 설정에는 readiness·종료 유예·리소스 제한을 포함하고, [Deployment 동작](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)을 실제 실행 환경에서 검증했는지 명시한다.

## 면접관이 직접 실행하는 데모

첫 화면에는 “AI가 확인한 뒤 정보가 바뀌면, 그 답은 아직 유효할까요?”라는 문제와 90초 체험 시작 버튼을 둔다. 로그인 없이 합성 시나리오를 체험한다. 고객 화면, 서버 상태, 사건 타임라인을 연결하고 더 깊은 기술 정보는 별도 탭에서 연다.

| 시간 | 면접관의 동작 | 화면에서 확인할 내용 |
| --- | --- | --- |
| 0초부터 20초 | 기본 사례 실행 | 고객 안내와 실제 API에서 받은 판단 기록 |
| 20초부터 45초 | 수취인 정보 변경 | 이전 결과의 무효화, 변경된 버전, 재확인 안내 |
| 45초부터 65초 | 모델 지연 또는 중단 | 대기 상한과 확인 필요 응답, 실패 원인 |
| 65초부터 90초 | 같은 상황 재실행 | 보호 장치 전후 비교와 관련 trace, 설계 이유 |

화면에는 실시간 서버 실행과 기록 재생을 명확히 구분한다. 서버 연결 실패 시 성공처럼 보이는 임의 데이터로 바꾸지 않는다. 기록 재생은 명시적으로 선택하는 보조 모드다. 비교용 기준선은 의도적으로 유효성 검사를 생략한 교육용 구현임을 표시한다.

보조 화면은 요청별 trace waterfall, 판단 기록 JSON 다운로드, 재현 명령, 설계 의사결정 세 개, 지원자로서 기여하고 싶은 방향을 제공한다. 오류 재현에서 출발해 원인 가설·대안 비교·선택 이유·회귀 테스트로 이어지는 해결 기록을 연결한다. 기존 경험에서 알려지지 않은 오류나 대화를 만들어 넣지 않고 이 프로젝트에서 실제 수행한 기록을 사용한다. 모바일·키보드 탐색·로딩·빈 결과·오류·초기화도 검증한다. 세션 간 시나리오가 섞이지 않게 격리하고 공개 데모 부하는 상한을 둔다.

## 검증과 성능 보고 기준

정합성 테스트는 추론 중 특징 갱신, 결과 생성 후 특징 갱신, 정책 변경, 모델 교체, 만료 경계, 멱등 요청 경쟁, 서버 종료 중 요청을 다룬다. 모델 서버 지연·중단·과부하와 DB 실패도 재현한다. 실제 네트워크 경계를 통과하는 통합 테스트와 브라우저 테스트를 포함한다.

성능 결과에는 하드웨어, 프로세스 수, 모델 해시, 데이터 시드, 부하 도구, 도착률, 동시성, 워밍업·측정 시간을 남긴다. 동일 조건으로 기준선과 보호 장치를 각각 반복 측정한다. 다음 값을 별도로 보고한다.

- 전체 제출 요청 수, 실제 완료 수, 기한 내 유효 결과 수

- 확인 필요 응답, 과부하 거절, 타임아웃, 재시도 수

- 전체 요청 및 결과 종류별 p50·p95·p99, 오류율, 자원 사용량

- 오래된 결과를 사용 가능하다고 반환한 위반 건수

- 고정된 합성 시나리오의 정책 분기 결과와 테스트 통과 여부

거절 응답이 빨라져서 전체 지연만 개선되는 현상을 성능 향상으로 포장하지 않는다. 수치는 실행 후에만 채운다. 정합성 시나리오의 기대 위반 건수는 0이며, 관측한 0건을 모든 가능한 실행에서의 수학적 보장으로 확대하지 않는다.

## 저장소와 결과물

새 저장소의 제안 이름은 recheck-ml-serving이다. 구성은 API, 모델 서버, 데모, 실험 스크립트, 배포 설정, 테스트, 문서로 나눈다. README 첫 화면에는 해결할 문제·데모 진입·재현 방법·주요 설계 판단을 배치한다. 연구 근거와 모델 카드, ADR, 장애 대응 기록, 실제 실험 결과, 90초 시연 대본을 함께 제공한다.

핵심 데모에는 유료 LLM API가 필요 없다. Claude는 나중에 판단 기록을 읽고 설명을 작성하는 선택 기능으로만 고려하며 모델 판정이나 유효성 검사에 대한 권한은 주지 않는다.

현재 GitHub 연결 앱에서 계정은 확인했지만 새 저장소 생성 도구는 노출되지 않았다. CLI는 네트워크 소켓 연결 단계에서 실패했으므로 토큰 무효라고 확정할 수 없다. 실제 저장소 생성과 push 가능 여부는 구현 단계에서 정상 연결을 확보한 뒤 확인해야 한다. 아직 원격 저장소와 실행 데모는 생성하지 않았다.
