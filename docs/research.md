## 공통점과 남겨 둔 차별점

위 사례에서 참고한 것은 대기열·채팅·랭킹이라는 소재가 아니라, 경쟁과 지연이 발생하는 구체적인 지점을 좁히고 선택의 근거를 남기는 방식이다. RECHECK는 유사한 서비스를 하나 더 만들기보다 다음 질문을 전면에 둔다.

**‘모델은 정상 응답했지만, 그 답이 참조한 세계가 이미 바뀌었다면?’**

| 흔히 보여주는 증거 | RECHECK가 추가하는 증거 |
|---|---|
| 모델 호출이 성공했다 | 모델 결과가 참조한 특징·정책·모델 epoch를 기록한다 |
| 빠른 API 응답 | 성공·추가 확인·수용 거절·오류를 모두 포함한 지연 분포를 보고한다 |
| 오류 처리 코드 | 보호 장치가 없는 기준선으로 오류를 재현하고, 켠 상태에서 같은 변경을 비교한다 |
| 기술 스택 그림 | 고객 안내 문구 → 버전 → 실패 사유 → 실제 분산 trace를 직접 연다 |
| 지원 직무의 키워드 | 사용자의 실제 ‘AI와 다른 해결책을 비교했던 경험’을 재현·가설·회귀 테스트라는 작업 방식에 연결한다 |

## 검토한 대안

- LLM 금융 상담: 소재가 흔하고 답변 품질·규제 설명이 서버 설계의 증거를 가리기 쉽다.
- 일반 송금/잔액 서비스: 정합성을 보여주지만 공고의 ML 추론 경계가 약하다.
- GPU 서빙 성능 경연: 사용자의 현재 경험과 실측 환경으로 운영 수준 성과를 정직하게 증명하기 어렵다.
- **선택 — 판단 유효성 실험실:** 작은 실제 모델로도 비동기 추론과 버전 변경의 경쟁을 재현할 수 있고, 지원자의 문제 해결 태도를 데모로 전달할 수 있다.

세계 최초 주제나 모든 지원자 대비 우위를 검증한 것은 아니다. 제한된 공개 조사에서 흔한 소재의 반복을 피하고, 면접에서 반박·재현할 수 있는 기술적 질문을 고른 결과다.

## 네 프로젝트의 실제 데모 조사

**현재 상태: 네 프로젝트 모두의 데모 경로를 조사했지만, 네 개 모두의 핵심 기능을 끝까지 실행한 상태는 아니다.** 책잇아웃은 공개 탐색 흐름을 실행했고, 새길은 설문 후반과 추천 오류 화면까지 확인했다. ChatTalk은 로그인 연결 후 공식 영상을 재생해 초반·중반·후반 일부 화면을 확인했다. CLASSMATE의 실행 데모는 찾지 못했다.

### 1. 새길 — 설문 후반까지 직접 이동

공식 [BE](https://github.com/CarToi/BE)·[FE](https://github.com/CarToi/FE) 저장소가 같은 배포 주소를 안내한다. 브라우저에서 시작 버튼을 누르고, 실제 사용자 정보가 아닌 임시 선택으로 기본 설문 7개와 기분 질문 2개를 진행했다. 선택 전후 버튼 활성화, 선택 카드의 강조·체크 표시, 상단 진행 막대와 이전/다음 버튼을 관찰했다.

공개 [추천 경로](https://saegil.vercel.app/recommend)에도 이동했다. 이 실행에서는 오류 안내가 표시됐고 추천 카드와 지도 결과는 확인하지 못했다. 정상 결과 UI를 봤다거나 추천 API가 정상 작동했다고 판단하지 않는다. 오류의 서버 측 원인은 별도로 진단하지 않았다.

공개 소스에서 질문 선택이 로컬 상태에 저장되고, 최종 전송과 만족도 저장은 별도 API 요청이라는 점을 확인했다. 조사 과정에서는 최종 전송·저장을 하지 않도록 제한했다. 전체 서비스 완료, 정상 추천 결과, 모바일 화면 검증은 미완료다.

- [실제 브라우저 실행 기록](https://agent.tinyfish.ai/runs/711db0e4-4157-4a72-8da5-ebafaca71d62)
- 소스 확인 버전: `CarToi/FE@298a2120011b14a898900af749908ab128e09501`
- UI에서 얻은 점: 질문 하나와 다음 행동을 묶고, 선택 여부와 진행 상태를 같은 화면에서 알려준다. 결과를 보기까지 단계가 많은 구조는 짧은 면접 데모에 그대로 적용하기 어렵다.

### 2. CLASSMATE — 실행 경로를 찾지 못함

[공식 팀 브로셔](https://prism-horse-a26.notion.site/Classmate-b9b08e51ffd441cea867a7aae5d1c930)에 접속했으나 페이지를 찾을 수 없다는 화면이 표시됐다. 저장소와 조직의 공개 링크는 이 브로셔를 가리킨다.

별도 조사에서 기본 브랜치 전체 **623개 커밋, README 8개 버전**, 프런트엔드·설정·코드의 URL, 팀원 5명의 공개 GitHub 프로필과 연결된 프로젝트 글을 확인했다. 실제 운영 사이트나 공식 시연 영상의 주소를 확인하지 못했다. 코드의 `quokkaws.shop`은 WebSocket 연결 대상으로만 나타나며, 사용자용 웹사이트 주소로 추정해 쓰지 않았다.

수강신청 표와 대기 인원·진행률을 보여주는 기존 화면 캡처는 보조 자료다. 검색·신청·대기열 기능을 직접 실행한 증거는 아니다.

- [브로셔 접근 확인 기록](https://agent.tinyfish.ai/runs/f86bc87d-a9e6-4bcc-a73a-042c981593c6)

### 3. ChatTalk — 로그인 연결 후 공식 영상 재생 확인

[공식 저장소](https://github.com/ChatTalk/.github)가 안내하는 [배포 사이트](https://chattalk-three.vercel.app)의 로그인·가입 폼을 확인했다. 계정을 만들거나 로그인하지 않았으며, 채팅방 진입·메시지 송수신·참여자 갱신은 직접 실행하지 못했다. 저장소에는 서버 인스턴스 연결 중단으로 시연 영상을 참고하라는 안내도 있다.

첫 [영상 접근](https://agent.tinyfish.ai/runs/65be681a-69ee-4c62-902c-77212aab1346)은 YouTube의 로그인·봇 확인에 막혔다. 사용자가 로그인 완료를 알린 뒤 같은 브라우저 프로필로 [공식 시연 영상](https://www.youtube.com/watch?v=FZV4JvbwLrQ)을 다시 열었고, **실제 재생에 성공했다.** 제목은 ‘ChatTalk 1차 기능구현 시연 영상’, 전체 길이는 1분 56초로 표시됐다.

| 실제 관찰한 영상 구간 | 화면에서 확인한 내용 |
|---|---|
| 약 0:03–0:05 | 이메일·비밀번호·역할 선택을 포함한 폼과 `Sign Up` 버튼 |
| 약 0:58–1:04 | 분할된 브라우저 화면, 사용자 정보와 `My Page`·`Log Out`, `Participants`·`Non Participants`, `Max Personnel: 3` 표시 |
| 약 1:17–1:32 | 채팅 메시지 목록, `Type your message...` 입력창, `Send`·`Leave` 버튼. 참여 여부를 구분하는 초록·빨강 표시와 ‘안녕하세요’, ‘수고하세요’ 등의 메시지 |

여러 시점의 재생 프레임을 확인했지만, 동일한 메시지가 여러 클라이언트에 도착하는 정확한 전후 시점이나 참여 상태가 바뀌는 순간을 짝지어 확보하지는 못했다. 표시된 상태를 확인한 것과 동기화 동작을 검증한 것을 구분한다. 영상은 `localhost`에서 촬영된 시연이며 현재 공개 서버의 정상 운영 증거가 아니다.

- [초반·중반 재생 확인 기록](https://agent.tinyfish.ai/runs/9a3920a1-b481-4143-8b73-1b2ad5c51e07)
- [후반 추가 확인 기록](https://agent.tinyfish.ai/runs/ed34f08e-fd38-4fb0-a84e-bfc8b16642cd)
- UI에서 얻은 점: 사용자 정보·채팅·참여 상태를 나란히 두고, 메시지 입력과 퇴장 버튼을 결과 가까이에 배치했다. RECHECK에서도 변경할 정보와 그 변경에 영향을 받는 판단을 함께 보여주는 구성이 유효하다.
- 관찰 한계: 마지막으로 확인된 시점은 1:32다. 1:56 최종 화면이나 전체 연속 시청을 완료했다고 표현하지 않는다. 작은 글자와 메시지별 타임스탬프는 정확히 판독하지 못했다.
- 근거 구분: 영상의 Kafka·Redis Pub/Sub 설명 문구는 작성자의 기술 설명이다. UI만으로 해당 구현·MSA 구조·전달 보장을 검증하지 않았다. 브라우저의 비밀번호 경고도 ChatTalk의 기능으로 집계하지 않는다.

### 4. 책잇아웃 — 공개 기능을 실제로 탐색

[작성자의 랭킹 구현 글](https://jinkpark.tistory.com/287)이 연결한 `booksitout.com`을 기준으로 조사했다. 검색 결과에 섞인 이름이 같은 다른 개발사의 독서 앱은 이 프로젝트로 취급하지 않았다.

브라우저에서 `Harry Potter`를 검색해 자동완성 결과를 열고, [선택한 책 상세](https://www.booksitout.com/book/9788983927811?q=Harry%20Potter)로 이동했다. 표지·저자·출판 정보·가격·서점 링크가 표시됐다. ‘서재에 추가’를 누르자 로그인 화면으로 이동했다. 계정 생성이나 저장은 하지 않았다.

이어 [베스트셀러](https://www.booksitout.com/community/popular-books), [추천인 목록](https://www.booksitout.com/community/book-recommendations), [추천인별 도서](https://www.booksitout.com/community/book-recommendations/ellen-degeneres), [꿀팁](https://www.booksitout.com/community/tips)을 실제로 탐색했다. 순위 목록에서는 순위·표지·책 정보·서점별 순위를 비교할 수 있었고, 추천인 목록에서 개별 도서 목록으로 이동할 수 있었다.

- [실제 브라우저 실행 기록](https://agent.tinyfish.ai/runs/d86781d4-604e-45ae-be2a-761590928b2c)
- UI에서 얻은 점: 로그인 전에 검색·상세·목록 탐색이 가능해 방문자가 먼저 기능을 경험할 수 있다. 개인 저장은 필요한 시점에 로그인으로 연결한다.
- 한계: 로그인 뒤 서재·독서 기록 기능은 미확인이다. 현재 베스트셀러 화면을 2023년 글의 게시글 Hot Ranking 구현 증거로 사용하지 않는다. 현재 서비스는 합격 이후에도 바뀌었을 수 있다.

### 조사에서 RECHECK로 가져갈 기준

1. **첫 행동이 바로 실행돼야 한다.** 로그인·환경 설정 없이 핵심 현상을 체험할 수 있어야 한다. 책잇아웃의 공개 탐색 흐름에서 확인한 진입 방식이다.
2. **행동 직후 달라진 상태를 보여줘야 한다.** 새길의 선택·버튼 활성화·진행 표시처럼, RECHECK도 변경한 정보와 판단 결과가 이어져야 한다. ChatTalk 영상에서 본 입력·메시지·참여 상태의 인접 배치는 행동과 결과를 같은 화면에서 읽게 하는 참고 사례다.
3. **배포가 멈추면 증거도 끊긴다.** CLASSMATE의 접근 불가와 ChatTalk의 서버·영상 진입 제한은 면접관의 체험을 막는다. RECHECK의 공개 브라우저 모드·실행 가이드·검증 기록은 계속 열려 있어야 한다.
4. **미확인을 성공으로 바꾸지 않는다.** 오류 화면·로그인 벽·링크 부재는 각각 그대로 기록한다. 코드·캡처·현재 서비스·과거 제출 버전은 서로 다른 근거다.

브라우저 실행 기록 링크는 해당 계정의 접근이 필요할 수 있다. 기록에 포함된 자동 번역이나 추정 표현은 보고서에 그대로 옮기지 않았다. 예를 들어 새길의 질문 제목·진행 표시 의미는 공개 소스와 대조하고, 추천 오류의 원인은 단정하지 않았다.

### RECHECK에 반영한 내용

참고 화면에서 적용한 것은 사용자가 할 행동과 현재 상태를 구체적으로 알려주는 문구다. 서비스 외관을 모방하거나 화면 자료만으로 운영 성능을 평가하지 않았다.

- 첫 제목은 **‘AI의 판단, 지금도 유효할까요?’**로 바꾸고, 수취인 정보를 바꿨을 때 이전 판단이 차단되는지 확인하는 데모임을 설명한다.
- 주 행동은 **‘오래된 판단 재현’**, 개별 실행은 **‘새 판단 요청’**, 사용 시점 확인은 **‘지금 사용 가능한지 확인’**으로 구분한다.
- ‘IMMUTABLE RECEIPT’, ‘CURRENT CUSTOMER MESSAGE’ 같은 장식성 영어를 ‘생성 당시 판단 기록’, ‘현재 확인 결과’로 바꾼다.
- 빈 화면은 구현 원칙을 설명하는 대신 다음 행동을 안내한다. 결과 표시는 변경됨·결과 무효·확인 필요처럼 상태를 바로 읽을 수 있게 한다.
- 지원자 소개는 사용자가 제공한 Python·LLM·AI/ML 경험과 AI와 해결 방법을 비교했던 경험에 근거한다. 은행 운영 경력이나 검증되지 않은 성과를 덧붙이지 않는다.
