## 공통점과 남겨 둔 차별점

위 사례에서 참고한 것은 대기열·채팅·랭킹이라는 소재가 아니라, 경쟁과 지연이 발생하는 구체적인 지점을 좁히고 선택의 근거를 남기는 방식이다. RECHECK는 유사한 서비스를 하나 더 만들기보다 다음 질문을 전면에 둔다.

**‘모델은 정상 응답했지만, 그 답이 참조한 세계가 이미 바뀌었다면?’**

| 흔히 보여주는 증거 | RECHECK가 추가하는 증거 |
|---|---|
| 모델 호출이 성공했다 | 모델 결과가 참조한 특징·정책·모델 epoch를 기록한다 |
| 빠른 API 응답 | 성공·추가 확인·수용 거절·오류를 모두 포함한 지연 분포를 보고한다 |
| 오류 처리 코드 | 보호 장치가 없는 기준선으로 오류를 재현하고, 켠 상태에서 같은 변경을 비교한다 |
| 기술 스택 그림 | 고객 안내 문구 → 버전 → 실패 사유 → 실제 분산 trace를 직접 연다 |
| 지원 직무의 키워드 | 사용자의 실제 ‘AI와 다른 해결책을 비교했던 경험’을 재현·가설·회귀 테스트라는 작업 방식에 연결한다 |

## 검토한 대안

- LLM 금융 상담: 소재가 흔하고 답변 품질·규제 설명이 서버 설계의 증거를 가리기 쉽다.
- 일반 송금/잔액 서비스: 정합성을 보여주지만 공고의 ML 추론 경계가 약하다.
- GPU 서빙 성능 경연: 사용자의 현재 경험과 실측 환경으로 운영 수준 성과를 정직하게 증명하기 어렵다.
- **선택 — 판단 유효성 실험실:** 작은 실제 모델로도 비동기 추론과 버전 변경의 경쟁을 재현할 수 있고, 지원자의 문제 해결 태도를 데모로 전달할 수 있다.

세계 최초 주제나 모든 지원자 대비 우위를 검증한 것은 아니다. 제한된 공개 조사에서 흔한 소재의 반복을 피하고, 면접에서 반박·재현할 수 있는 기술적 질문을 고른 결과다.

### RECHECK에 반영한 내용

참고 화면에서 적용한 것은 사용자가 할 행동과 현재 상태를 구체적으로 알려주는 문구다. 서비스 외관을 모방하거나 화면 자료만으로 운영 성능을 평가하지 않았다.

- 첫 제목은 **‘AI의 판단, 지금도 유효할까요?’**로 바꾸고, 수취인 정보를 바꿨을 때 이전 판단이 차단되는지 확인하는 데모임을 설명한다.
- 주 행동은 **‘오래된 판단 재현’**, 개별 실행은 **‘새 판단 요청’**, 사용 시점 확인은 **‘지금 사용 가능한지 확인’**으로 구분한다.
- ‘IMMUTABLE RECEIPT’, ‘CURRENT CUSTOMER MESSAGE’ 같은 장식성 영어를 ‘생성 당시 판단 기록’, ‘현재 확인 결과’로 바꾼다.
- 빈 화면은 구현 원칙을 설명하는 대신 다음 행동을 안내한다. 결과 표시는 변경됨·결과 무효·확인 필요처럼 상태를 바로 읽을 수 있게 한다.
- 지원자 소개는 사용자가 제공한 Python·LLM·AI/ML 경험과 AI와 해결 방법을 비교했던 경험에 근거한다. 은행 운영 경력이나 검증되지 않은 성과를 덧붙이지 않는다.
