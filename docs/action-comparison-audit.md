# 검증 시점과 SQL 기록: 감사 및 비교 실험

감사 기준: 2026-10-11. 상담 검토 화면 배포 이후의 서버 코드와 기존 실험을 대조했다.
이 문서는 기술 검증 기록이다. 지원자의 개인 기여나 채용 결과를 입증하는 자료가 아니다.

## 먼저 확인한 것

| 확인할 주장 | 기존 근거 | 감사 결과와 이번 조치 |
| --- | --- | --- |
| 검사 후 기록 전에 변경되면 오래된 결과가 실행될 수 있다 | `evaluate_safety.py`의 9개 고정 사건, 실제 SQL 레코드 집계 | 이미 구현. 비교기를 새로 만들었다고 주장하지 않고 유지 |
| 검증과 기록이 원문 변경과 같은 잠금을 사용한다 | `EvidenceStore.execute`, `event`, `promote`; 실제 두 연결의 잠금 경쟁 테스트 | 이미 구현. 생산 코드에 불필요한 우회 경로나 테스트 훅을 추가하지 않음 |
| 같은 요청이 겹쳐도 작업이 한 번만 기록된다 | API 동시 요청 테스트, 작업 이력 조회 | 6개 동시 요청 × 12회차를 세 방식에서 반복해 전체 응답과 SQL 기록 보존 |
| 완료 후 근거가 바뀐 재시도는 과거 결과를 반환한다 | `execute`는 멱등 키 조회를 현재 유효성 검사보다 먼저 처리 | 세 방식의 비교 실험으로 확장. 과거 결과 반환을 오래된 신규 실행과 분리 |
| 검증에 어느 정도 비용이 드는가 | 해당 SQL 경로의 동일 조건 시간 측정 없음 | 예열 후 정상 기록 90회씩, 순서를 회전해 p50·p95 측정 |
| 데모에서 비교의 원인을 확인할 수 있다 | 합계 표와 저장소 링크만 표시 | 9개 사건 선택, 실제 원문 전후·검사 응답·기록·작업 ID 표시. 동시 요청과 비용 표 추가 |
| 표시 수치가 현재 코드에서 나온 결과인가 | 원본 JSON ↔ 요약 일치만 검사 | 현재 소스 SHA-256 ↔ 측정 원본도 검사. 오래된 코드의 측정치는 CI 실패 |

기존 트랜잭션 구현을 이번에 새로 만든 것으로 계산하지 않는다. 이번 변경은 비교기의 관측 범위,
회귀 검증, 증거의 최신성 확인과 실제 SQL 결과를 탐색하는 화면을 보강한다.

## 비교 설계

세 방식 모두 실제 같은 `Store`·`EvidenceStore`와 SQL 잠금, 같은 키 중복 제거를 사용한다.
비교 기준선의 무검증 쓰기는 **오프라인 스크립트에만** 존재한다. 공개 API는 보호된 쓰기만 제공한다.

1. **생성 결과 신뢰:** 원문을 다시 검사하지 않고 멱등 기록.
2. **검사 후 별도 기록:** `use`로 검사한 뒤, 별도 트랜잭션에서 멱등 기록.
3. **검증과 기록 결합:** 생산 코드 `execute`로 멱등 조회 → 현재 근거 검사 → 기록을 같은 트랜잭션에서 처리.

검사 후 별도 기록은 검사에 실패하면 기록 함수에 도달하지 않는다. 따라서 완료된 작업의 근거가
바뀐 뒤 같은 키를 다시 보내면 기존 결과의 반환도 막힌다. 이 결과는 중복 제거가 없어서 생기는
차이가 아니라 **검사와 멱등 조회의 순서**에서 생기는 차이다.

### 동시 요청: DB마다 같은 5가지 조건

각 방식·조건에 대해 6개 스레드가 독립 연결로 요청하며 12회차를 실행한다. 회차마다 새 세션과 같은
검색 결과를 준비한다. 준비와 별도 검사를 마친 뒤 동기화 장벽을 열어 기록 요청을 함께 시작한다.
방식의 실행 순서는 회차별로 회전한다. 스레드 동시성의 보장은 프로세스·호스트 분산의 보장이 아니다.

| 조건 | 변경과 요청 순서 | 확인할 결과 |
| --- | --- | --- |
| 같은 키 | 준비 → 검사 기회 → 같은 키 6개 | 회차당 새 작업 1개, 기존 작업 응답 5개 |
| 다른 키 | 준비 → 검사 기회 → 다른 키 6개 | 회차당 유효한 새 작업 6개 |
| 검사 후 변경 | 준비 → 모든 별도 검사 완료 → 원문 변경 커밋 → 같은 키 6개 | 변경된 근거로 새 작업이 기록되는지 |
| 변경 후 과거 작업 재시도 | 준비 → 유효 작업 1개 기록 → 원문 변경 → 같은 키 6개 | 새 작업 없이 과거 작업 반환 |
| 잠금 시간 초과 후 재요청 | 실제 SQL 잠금 유지 → 같은 키 6개 시간 초과 → 잠금 해제 → 같은 키로 재요청 | 첫 오류 보존, 재요청 후 작업 1개 |

응답 수와 새 작업 수는 다르다. 검사 후 변경 조건에서 기준선은 회차당 오래된 작업 1개를 만들고
나머지 요청에 그 작업을 반환할 수 있다. 이를 오래된 신규 기록 6개라고 세지 않는다.
원본에는 회차별 요청 결과, 검사 응답, 초기 SQL 작업과 최종 SQL 작업을 함께 남긴다.
전체 수 외에도 키별 기록 수와 응답 ID에 연결된 키·receipt를 대조한다. 한 키의 중복과
다른 키의 누락이 합계에서 상쇄되는 결함을 실제 SQL에 주입해 검출하는 회귀 검사도 포함한다.

DB 오류가 발생하면 동시 요청 단계가 끝난 후 해당 요청만 같은 세션·receipt·키로 **한 번** 재요청한다.
세 방식에 같은 규칙을 적용하며 검사 후 별도 기록은 검사부터 다시 수행한다. 검증 거절은 재시도하지 않는다.
최초 응답·복구 요청·복구 전후 SQL 스냅샷을 모두 저장하고 두 스냅샷에서 중복·오래된 쓰기를 검사한다.
첫 오류 수는 그대로 표시하며, 미복구 오류와 필수 최종 응답의 실패는 검증을 실패시킨다.
이는 경쟁이 해소된 후의 복구이지 지속적인 부하 중 가용성을 보장하는 실험이 아니다.

### 비용: 동시성 실험과 분리

방식별 9회 예열 후 90회. 각 표본은 새 세션의 같은 준비된 답변과 빈 작업 목록에서 시작한다.
세 방식의 선후 순서를 회전하고, 직접 Store 함수의 검사·기록 호출부터 SQL 커밋까지
`perf_counter_ns`로 측정한다. 정상 경로의 동시성은 1이다.

HTTP, 검색, 세션 생성, 결과 확인, 정리, 경쟁 조건을 만들기 위한 장벽 대기는 측정에서 제외한다.
실패 표본도 삭제하지 않으며 성공 수·전체 요청 수를 함께 표시한다. 분위수는 nearest-rank 방식이다.
같은 호스트와 풀을 공유한 짧은 측정이므로 작은 차이의 유의성이나 실서비스 처리량을 주장하지 않는다.

## 관측 결과

SQLite와 PostgreSQL에서 각각:

| 방식 | 검사 후 변경: 오래된 신규 기록 / 12회차 | 같은 키: 중복 기록 / 12회차 | 변경 후 재시도: 기존 작업 반환 / 72회 요청 |
| --- | ---: | ---: | ---: |
| 생성 결과 신뢰 | 12 / 12 | 0 / 12 | 72 / 72 |
| 검사 후 별도 기록 | 12 / 12 | 0 / 12 | 0 / 72 (72회 거절) |
| 검증과 기록 결합 | 0 / 12 | 0 / 12 | 72 / 72 |

각 DB에서 보호된 구현은 정상 단일 요청 90/90, 서로 다른 키의 동시 요청 72/72를 기록했다.
검사 후 변경 요청 72/72는 `source_changed`로 거절했다. 같은 키 요청은 12개 작업과 60개 재시도
응답으로 수렴했다. 세 방식의 네 동시 요청 조건에서 관측된 DB 오류는 0건이다.

다섯 번째 조건은 오류를 의도적으로 재현한다. 세 방식 각각 첫 요청 72회가 실제 DB 시간 초과로 실패하고,
잠금 해제 뒤 72회 재요청을 처리했다. 회차당 최종 작업은 1개이며 처음 오류를 성공으로 바꿔 집계하지 않았다.
별도 API 테스트도 실제 잠금 시간 초과가 HTTP 503 `database_unavailable`로 노출되고 같은 키로 복구되는지 확인한다.

시간 수치는 [측정 원본](evidence/action-workloads.json)의 DB별 `strategies[].latency`와
[공개 데모](https://sokldjs554.github.io/recheck-ml-serving/)의 **세 방식 비교**에서 확인할 수 있다.
표시되는 시각·런타임·소스 해시도 해당 실행의 값이다. CI의 축소 반복 결과와 이 측정치를 혼합하지 않는다.

## 재현 및 변경 검출

```bash
PYTHONPATH=backend backend/.venv/bin/python -m pytest backend/tests/test_action_workloads.py backend/tests/test_safety_evaluation.py -q
backend/.venv/bin/python scripts/evaluate_safety.py
backend/.venv/bin/python scripts/evaluate_action_workloads.py
python scripts/build_safety_summary.py
python scripts/build_safety_summary.py --check
```

기본 실행은 임시 SQLite만 측정한다. 두 DB를 포함하려면 두 평가기에
`--postgres-url-env RECHECK_EVAL_DATABASE_URL`을 전달하고 그 환경변수에 **폐기 가능한 테스트 DB**의
연결 문자열을 설정한다. 연결 문자열은 결과에 저장하지 않는다. 평가기는 자신이 만든 세션을 정리하지만
기존 세션 보존 정책도 적용하므로 실제 운영 DB를 사용하지 않는다.

회귀 검사는 보호된 쓰기를 무검증 쓰기로 바꾼 경우, 정상 요청을 전부 거절하는 경우, 중복 제거를
제거한 경우를 실제 SQL 결과에서 발견한다. 보호된 결과가 조건을 위반하면 평가기는 성공 파일을 쓰지 않는다.
전체 실패 응답은 별도 `*.failed.json`에 저장하고 종료 코드는 실패로 반환한다. 기존 성공 자료는 덮어쓰지 않는다.
화면 생성기는 통과 표시가 없는 측정 원본을 거절한다.

CI에서는 두 DB에 회차 3회·정상 표본 12개로 축소 재현해 아티팩트를 남긴다. 시간에 합격선을 설정하지 않는다.
화면은 원본에서 자동 생성되며, 사건 선택·DB 선택·과거 ID·JSON 다운로드·모바일 표시를 브라우저에서 확인한다.

### 이번 검증에서 드러난 한계

개발 중 한 차례 `replay_after_edit missing_replays=1`로 측정이 실패했다. 당시 평가기는 실패 전에
상세 응답을 저장하지 않아 그 한 요청의 원인을 특정하지 못했다. 이후 두 DB에서 50회차씩 진단했지만
같은 실패는 재현되지 않았다. 이 최초 실패를 DB 시간 초과나 복구 성공으로 소급 분류하지 않는다.
실패 파일 보존과 명시적인 DB 시간 초과·재요청 실험을 추가한 이유이며, 새 자료에서도 논리적 거절은
운영상의 오류로 바꾸거나 재시도해 숨기지 않는다.

## 여전히 입증하지 않은 것

- 임의의 사건 순서 전체, 지속적인 고부하, 여러 호스트, 시계 오차·장애를 포함한 일반적 안전성.
- 외부 메시지 발송이나 송금의 원자성. 별도 outbox·멱등 수신자 계약이 필요하다.
- 큰 문서 집합, 실제 LLM 품질, 실제 고객 지표. 이 실험은 작은 가상 문서와 SQL 기록을 사용한다.
- 실제 사용성 조사와 개인별 구현 기여. 자동 검사·AI 협업 기록이 이를 대신하지 않는다.

성능 확장의 후보는 세션 JSON과 단일 행 잠금의 경합을 더 큰 상태·서로 다른 세션으로 측정하는 것이다.
이번 자료만으로 JSON 구조가 대규모 작업 원장에 적합하다고 결론내리지 않는다.
