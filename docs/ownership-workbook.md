# 직접 판단하고 검증하는 개발 과제

이 문서는 지원자의 수행 이력이 아닙니다. 아래 과제는 아직 본인이 수행했다는 증거가 없습니다.
AI가 만든 설명을 외우는 대신, 실행 전 예측 → 코드 변경 → 반례 → 측정을 자신의 기록으로 남깁니다.
정답 개수나 완료 체크만으로 역량을 인증하지 않습니다. AI를 사용해도 되며 어떤 제안을 검증·기각했는지 적습니다.

## 1. 확인했는데 왜 오래된 답이 실행될까?

먼저 `python scripts/evaluate_safety.py --help`와 [비교 실험](safety-case-study.md)을 봅니다.
결과 JSON을 읽기 **전에** 다음 순서의 결과를 예측합니다.

`답변 준비(v1) → 사용 가능 확인 → 원문 수정(v2) → 내부 작업 기록`

- 생성 시점만 신뢰하는 방식은 어느 시점의 사실을 알고 있나요?
- 사용 직전에 확인했는데도 실패하는 이유는 무엇인가요?
- `EvidenceStore.execute`가 잡은 잠금과 `event`의 잠금이 다르면 어떻게 되나요?
- 작업 기록 이후 원문이 바뀌면 과거 작업 기록을 삭제해야 할까요?

직접 수행: 별도 브랜치에서 `execute`의 유효성 검사를 잠금 밖으로 옮기는 작은 변경을 만드세요.
기존 동시성 테스트가 실패하는지 확인하고, 실패하지 않는다면 사건 순서를 제어하는 테스트를 추가하세요.
실험 후 위험한 변경은 되돌립니다. 운영 코드에서 안전 장치를 제거해 배포하지 않습니다.

검증 명령: `PYTHONPATH=backend backend/.venv/bin/pytest backend/tests/test_evidence_actions.py -q`.
제출 근거: 예측, 실제 실패 로그, 최소 diff, 수정 후 로그, 검사가 원자적인 지점을 표시한 설명.

## 2. 재시도는 새 실행인가, 과거 실행의 확인인가?

먼저 정상 작업을 기록한 다음 원문을 수정합니다. 같은 요청 키로 재시도하면 어떤 응답이 맞을지 적습니다.
그 뒤 다른 답변 ID에 같은 키를 쓰는 경우와 비교합니다.

직접 수행: SDK에서 네트워크 응답 유실 후 재시도하는 호출 예제를 만드세요. 서버가 이미 기록했지만
클라이언트가 응답을 못 받은 경우에도 작업 ID가 하나만 생겼는지 GET actions로 확인합니다.
새 키를 발급하는 잘못된 재시도와 비교하고, 키를 누가 언제 생성·보존해야 하는지 설명하세요.

제출 근거: 요청 키와 작업 ID를 포함한 두 실행 기록, 중복 방지 경계, 세션 만료 시 한계.

## 3. 내부 DB 밖으로 나가면 무엇이 달라질까?

현재 작업 기록은 외부 메일·송금·티켓 서비스에 전달되지 않습니다. 외부 API에 실제 호출하지 않고,
실패 가능한 가짜 수신기를 로컬에서 만들어 다음 두 순서를 비교하세요.

- 외부 API 호출 후 DB 기록: 외부 성공 직후 프로세스가 종료되는 경우.
- DB 기록 후 외부 API 호출: DB 성공 직후 프로세스가 종료되는 경우.

직접 수행: 둘 중 하나에 대한 재현 테스트를 작성한 뒤 outbox와 수신기 멱등 키를 설계합니다.
외부 시스템이 멱등성을 지원하지 않으면 정확히 한 번의 외부 효과를 어떤 근거로 보장할 수 있는지 따져보세요.
현재 프로젝트가 이미 이 문제를 해결했다고 설명하면 안 됩니다.

## 4. 복잡한 구조를 줄일 수 있는가?

[CPU 비교 실험](compute-experiments.md)에서 한 요청률을 선택하세요.
처리량, 시간 내 성공, 상태 확인 지연, 메모리를 함께 읽고 프로세스 분리가 필요 없는 조건을 적습니다.
호스트 부하와 짧은 관측 기간 때문에 결론이 바뀔 수 있는 조건도 적으세요.

직접 수행: 자신이 선택한 조건으로 실험을 재현합니다. 개선이 없거나 나빠졌다면 그대로 기록합니다.
원래 실험과 다른 컴퓨터의 수치를 직접 묶어 개선율을 만들지 않습니다.

